## 缓存策略

评测过程默认采取一种保守的缓存策略：

1. 缓存键与评测代码的 git commit 直接相关，只有在同一个 commit 下多次运行时才会复用缓存，也即，对代码的任何改动都会导致缓存失效；
    - 由于我们无法评估代码改动对评测结果的影响，因此我们选择在代码改动时不复用缓存，以保证评测结果的可靠性；
2. 只有当评测过程被中途中断（比如中途异常退出）而未能得到最终结果时才会保留缓存；当正常结束时默认会清理缓存；

因为缓存最常见的使用场景是，当代码已经固定下来，但评测运行过程被意外中断了后立即在现场重新运行。
因此，上述缓存策略对于这一常见场景是合理的。
对于更为复杂的缓存复用，由于我们无法保证所有接入的外部系统都一定具有某种能力，所以贸然假设然后做更激进的缓存复用可能会导致评测结果不可靠。

## 缓存内容

- 用于运行任务的所有 snapshots，用于避免重复构建 snapshot 的 overhead；
- 一次完整运行并正常结束的 trail 的所有 events，用于完整重放 trail 的运行过程；

## 长程任务的缓存

对于长程任务，多 stage 被认为是必须的，而且必须做到：

- sandbox 状态是可恢复的，也即同一个 sandbox 在重启之后仍然能作为合法的环境；
- 每个 stage 都是独立的，也即在一个 stage 结束后在运行下一个 stage 时 agent 新开一个 session 来运行仍然可以正常运行；

如果能够做到如上两点，则缓存内容还可以包括 trail 的 sandbox 以及该 trail 目前已经正常运行完成的 stages 记录。
下一次运行时将会重新启动 sandbox 并从上一次运行完成的 stage 继续运行。
