- agent 应当接受如下几种 tools 设置：
  - 手动传入 effect toolkit；
  - 若干 skills，如果提供则会被作为一个统一的 skillTool 提供；
  - 对于 mcp/cli，使用memfs提供一个兼容层，统一将它们以 skill 的形式进行暴露；

## Context 管理

- Context 管理本质上需要评估将一个旧上下文驱逐带来的未来可能收益和造成的前缀缓存失效代价之间的权衡。

### 文件阅读/编辑上下文

- 让 agent 维护一个编辑器的概念，它自行决定维护一组打开的文件，这些文件在上下文的某一处是出现过的；
- agent 自行选择文件的关闭管理，关闭后上下文将会被从上下文中驱逐掉；
- 编辑文本总是会将旧版上下文驱逐（如果缓存代价可以接受），并将新版本的上下文加入到上下文中；

### 异步消息管理

- 首先是最基础的 排队 模式和 steer 模式；
- 然后是一个外部的 event store 用于根据种类汇总所有来源的外部消息；
- 最后是 agent 如何介入消息的接收环节，或许可以让 agent 自行选择调用工具查询 event store？

### 长程状态管理

长程任务的核心在于两点：

1. 阶段验收标准
2. 状态恢复机制

对于 1，必须在启动任务之前就根据任务本身的语义把验收图 DAG 构建好；
这个图必须是 agent 无关的，完全出自于任务目标本身的业务需求；
在执行过程中可以根据实际情况对图中的边进行细化（比如把边替换成子图），但不能改变图的拓扑结构；

对于 2，必须假定 agent 在任何阶段都可能被中断，向死而生；
在这种前提下当 agent 再次恢复时必须能够立即承载中断前的上下文，并能够清晰确认中断前的目标。

执行框架整体必须围绕类 GitHub 的系统，包括 git，issue，PR 等机制；

为了防止 staled 的状态导致 rotting，严格禁止积累未经版本管理/任务跟踪的文档/知识库什么的，把最新代码当作唯一事实源；
